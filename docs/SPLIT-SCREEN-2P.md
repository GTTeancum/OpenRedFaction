# Two-player split screen (PS2) — design

Status: stages 1-2 done, stage 3a done, stage 4 views done, stage 3b bots and
scoring done (2026-11-06). Two players only
(the PS2 limit); the engine's quarter-screen layouts are never used.

## PS2 behaviour (traced)

- Mode popup "Player vs Player" (1e3cd0 area): requires a second controller
  (2389a0(1)); without one it shows an error popup; with one it sets two
  humans (1dda20(2), `2ab9e8`) and enters PLAYER NAME (0x17).
- Player records `2ac2b0` (player 1) and `2ac2b4` (player 2), count `2ac2b8`.
- Viewports (1a5ba0, set at match start 113253): player 1 case 2 (top half),
  player 2 case 3 (bottom half); 90 degree field of view (0x42b40000) for both.
  Cases 4-7 (left/right halves, quarters) exist in the engine but the game
  never uses them.
- Menus already traced have two-human variants: PLAYER NAME and CHARACTER
  panels side by side (26bdc0/26ca40 with x0 per player), MP OPTIONS list
  290ee0 with "Player 2 Options" (rows at 0x106/0x11a/0x142), arena bot limit
  = first `$Num bots` value (4 on most arenas).
- HUD: split-screen offsets in 1a9c20, 1abd00, 1acc70, 1af170 and the
  multiplayer parts of 160f40 (not yet traced); the respawn prompt sits at
  y 175 instead of 350; the end screen draws a divider.
- Bots treat both humans as players (12b830 "no human players" = neither of
  the two records).

## Port today

- One player: about 400 player globals (rf_scene_actor_*, actor_*,
  campaign_player_*, scene_player_*, rf_scene_player_*) with about 1,800
  references across scene.c and its .inc files.
- scene_frame (scene.c) interleaves the player's movement and ground
  handling, the world and NPC update, then builds one mesh of draws culled
  for the player's view and hands it to one presentation sink, which flips.
- The player body is a collision participant (scene_actor_body,
  campaign_player_object) that NPC targeting, hits and pickups refer to by
  one handle.

## Design

1. Player context: gather every player-owned global into per-player storage
   (a context block). The live globals stay where they are; a swap copies one
   player's block in and the other's out, so existing code is unchanged.
   Shared world state must never be in the block. Registered objects need
   one registration per player, so player 2 gets its own entity view and
   handle, and the swap exchanges the registry pointer target as well.
2. Frame split: scene_frame is divided into a per-player phase (input,
   stance, ground, movement, weapons, damage, pickups, camera) and a world
   phase (NPCs, projectiles, movers, effects). Each frame runs the world
   phase once and the player phase once per human with that player swapped
   in.
3. Two bodies in the world: collision, hit tests, pickups, explosions and
   NPC targeting must see both player bodies (the places that use
   scene_actor_body / campaign_player_object.handle directly take a list).
4. Two views: the draw preparation (visibility, NPC/clutter/weapon draws,
   first-person weapon) runs per player into the shared mesh buffer, and the
   presentation sink draws each into its half (top/bottom, 90 degree field)
   without flipping, then flips once. In widescreen the pair is pillarboxed
   to a 4:3 area.
5. HUD per half from the traced PS2 split offsets; input from controller 1
   and 2; MP STATS, end screen and scoring for two humans; Player vs Player
   menus.

## Stages (each builds, is committed and smoke-tested)

1. Inventory the player globals and build the swap with a self-test (swap
   twice per frame with one player: behaviour unchanged).
2. Split scene_frame into world and player phases (one player: unchanged).
3. Player 2 body, registration and spawn; both bodies in collision and
   targeting; player 2 driven by controller 2 (or the harness).
4. Two views top/bottom with pillarboxing; per-player HUD.
5. Player vs Player menus, two-human options list, MP STATS and end screen.

Main risks: a missed global leaks state between players; memory (a second
first-person weapon and HUD state within stock 64 MiB); frame rate with the
world drawn twice (each view is half the pixels, but draw preparation
doubles).

## Stage 1 result

- `src/diagnostic/scene_player_context.inc`, generated by
  `tools/split2p/gen_ctx.py` from the no-LTO scene object's symbol table
  (`tools/split2p/globals.py`) and the name rules in
  `tools/split2p/classify.py`: 201 per-player values, 159,180 bytes;
  `scene_player_exchange` swaps them with one parked block,
  `scene_player_select(slot)` and `scene_player_clone()` are ready for
  stage 3.
- Left out for now: function-local statics (scene_use_edge,
  scene_scope_owner, scene_player_outside_audio, scene_weapon_loop_audio,
  scene_scanner_collect, riot shield definitions); state in other files
  (renderer HUD and first-person weapon view) is not yet inventoried.
- Self-test (`--player-swap-test`, D:\player-swap-test.flag): four
  exchanges per frame. Hangar 18 bot match and the developer testbed
  behave as without it (testbed: same 32 shots and 2 weapon switches). A
  byte-by-byte exchange was slow enough to disturb timing; the exchange
  copies in 4 KiB chunks.

## Stage 2 progress

- `scene_player_prepass` (room refresh, ground check and material,
  movement command) and `scene_player_physics(..., primary, ...)` (forces,
  support, movement, landing, footsteps, liquid and outside damage) are
  extracted from scene_frame and called once; the movers, vehicles, NPC
  support and mover commit inside the physics step run only when `primary`
  is set. Developer testbed and a bot match unchanged.
- Found while mapping: the frame loop is driven by the player's animation
  (`animation_run` in src/diagnostic/animation.c), which holds the player's
  model, skeleton, motion state and animation controller as locals and calls
  the camera/combat callback (`actor_follow_view`, which also runs the
  player's weapon fire) and then scene_frame. Player 2 therefore needs a
  second animation driver (own model, skeleton, motions, controller), added
  beside the single-player one rather than restructuring it.
- actor_follow_view: `scene_follow_primary` (default 1) guards its world
  updates (vehicles, turrets, NPC and precision rounds, ambient audio and the
  listener, message audio, NPC eye publication for spit/cane AI, test
  fixtures, checkpoints and saves; 37 statements). The player's use action,
  rounds, tracers, camera, camera effect, combat, empty-weapon handling and
  scope still run for any human. The view build (visibility, static world,
  movers, terrain into stream->mesh) is `scene_follow_build_view`, callable
  for any camera (stage 4). Testbed and bot match unchanged; the view draws
  correctly.

## Stage 3a: a second human that moves

- Animation driver: `secondary_select` on the placement; after the primary's
  prepare_view each frame the driver runs the second human's stance,
  movement, playback, pose and prepare_view with its own playback state,
  controller and resource table on the shared model (src/diagnostic/animation.c).
- Scene: `split-test.flag` (`--split-test`) creates the second human at the
  first frame from a copy of the first (own copy of the collision spheres,
  placed on a multiplayer player point), with fixed test input (walk and
  turn, bursts of fire). Its pre-pass and physics step run after the
  primary's with its state live. `rf_scene_split` reports it.
- The per-player table grew to 227 values: `tools/split2p/used_by.py`
  lists globals the player's routines use that the table lacks; it found the
  collision body, support state, equipped slot, trigger and weapon-runtime
  state the name rules had missed.
- World work inside the player's combat routine (bot combat AI, AI weapons,
  world grenades and rockets, burning, drops, turrets, vehicles, rubble,
  the multiplayer match update and bot pickups) now runs for the primary
  human only, as in the follow view.
- Checked: one player unchanged (testbed same shots and switches); with the
  second human the match clock runs at the normal rate and the second human
  moves on its own (65 positions in two minutes).
- Not yet: the second human has no view (stage 4); grenades and rockets
  share one routine with the world's grenade/rocket flight, so the second
  human cannot throw or launch them yet; bots, hits and pickups of others
  do not see the second human, which still carries the first's entity
  handle (stage 3b); input is the test pattern (stage 3c); its sphere copy
  is not freed at the end of a match.

## Stage 4: two views

- Each frame the primary human's view draws into the top half, then the
  second human's view (its camera kept from its follow view, its state live)
  is built and drawn into the bottom half of the same picture, as the PS2
  (1a5ba0 cases 2/3). `rf_scene_split_view` tells the renderer which half:
  the top pass waits for VBlank and clears the picture to black, the bottom
  pass continues it and flips. Widescreen keeps both halves inside the
  centred 4:3 area (960 of 1280 pixels, black side bars).
- Cameras squeeze vertically by two and drop the widescreen squeeze while
  split; visibility uses the plain 4:3 frustum.
- The scene's draw preparation is one routine run once per view; the second
  view skips draws that age state when submitted (debris, ripples). The
  frame hand-off accepts the second view without counting a new frame, and
  the presentation decision of the top view holds for the bottom.
- The renderer rewinds the command buffer before the bottom view (the top
  view's commands are already submitted and the GPU idle).
- Checked in XEMU: both views on screen (top player dead with its respawn
  prompt, bottom player armed and moving); a 3,600-frame match with two
  humans ran to the end; one player unchanged (testbed 32 shots, 2
  switches; bot match normal). Speed in XEMU: one player about 29 fps, two
  players about 22 fps (game work per picture 16 ms against 44 ms).
- Not yet: the HUD is still one full-screen layout drawn in each half (the
  PS2 per-player layout is stage 5); the two-player cost needs a look on
  hardware.

## Stage 3b: the world sees the second human

- The second human gets its own entity handle at creation. The registry
  slot names the player globals, which hold whichever human is live, so
  "is this the player" checks stay true only for the live human. Words in
  the copied per-player state equal to the first human's handle (7 of them:
  weapon runtimes, charge state and the like) are rewritten to the second's.
- `src/diagnostic/scene_split_humans.inc` reads either human, live or parked,
  by index or handle (`scene_player_other` finds a global's parked copy).
- Bots: target choice weighs both humans (12b580's candidate list); route
  aim, aim pose, sight checks and the attack update find either human.
  Bots fighting the second human run their update in that human's pass with
  it live (the set is taken once per frame in the first pass, so each bot
  updates once a frame); their flying rounds also fly in that pass.
- Scoring: the second human's kills, deaths and streaks are kept in
  `rf_scene_mp_human2`; the kill limit counts them. Each human's death is
  scored in its own pass, and the respawn fade is per human.
- Fixed on the way: the combat routine's once-per-frame guard was shared,
  so the second human's combat never ran (stage 3a's "fire bursts" did
  nothing); the respawn fade and fire-held state were shared. The test
  pilot tapped fire to respawn only on odd frames, which two-player pacing
  never reached (the bots then stood still with no live target).
- Checked in XEMU (dm05, 4 bots, 3,600 frames): bots fought the second
  human on 937 frames, shot at it 35 times and hurt it 17 times; it died and
  respawned; the first human died and respawned 4 times; the match ran to
  the end. One player unchanged (bot match, testbed 32 shots, 2 switches).
- Not yet: a round aimed at one human cannot hit the other; the second
  human's model is not drawn in the first's view (and the reverse); the
  bodies do not collide with each other; pickups for the second human;
  controller 2 (stage 3c); HUD per player (stage 5).
