# Force_Monitor_Update save boundary

L6S3 cutscene UID 3696 has a frame-60 ordinary save veto: event UID 6644 (`Force_Monitor_Update`, type 60) is queued with deadline 1016 ms. The same event remains queued in later PC probes (deadlines 4016 ms at frame 180 and 10016 ms at frame 600), so waiting a few seconds does not establish a safe save window. The new image-free regression asserts this exact early veto. Generic event checkpoint serialization now accepts type 60 when inactive, but marks it unimplemented so a pending dispatch remains rejected on both capture and restore. This does **not** claim type-60 gameplay is implemented.

Original `RF.exe` SHA-256 `b8fb9ab4c9bfc6f2868c30839d6cfc69f84b8c25d7e54eee1325f5b633c9b836`: allocator `0x4b69d0` routes type 60 through the base event class, whose on-action vtable entry is `0x4b9070`. Its type-60 case calls `0x4b9af0`. The raw Ghidra export of `0x4b9af0` iterates the global object list, selects object kind 4 with class flags bit `0x8` at class offset `0x74`, then calls `0x412990` with the entity handle. `0x412990` looks up a separate monitor entry by that handle (`0x412650`) and clears bit `0x4` at monitor-entry offset `0x38`. The observed operation is a forced monitor update request, not an authored-link dispatch. Type 49 (`Monitor_State`) has a separate on-action `0x4ba980` that configures the monitor entry and linked entity relationships through `0x412600` and `0x4126a0`.

The current port has no equivalent monitor-entry table or persistent dirty-bit state. Implement that owner and its normal polling/linked effects before allowing a queued type-60 save or claiming L6S3 continuation fidelity. Ghidra exports are local under `artifacts/analysis/rf_b8fb9ab4c9bf/`; the addresses above are binary-derived evidence, while the gameplay integration and save ABI remain open.
